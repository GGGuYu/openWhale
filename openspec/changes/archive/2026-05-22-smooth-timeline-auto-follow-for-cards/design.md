## Context

当前时间线已经有“贴近底部时自动跟随”的基础要求，但实际体验仍偏向文本流式增长场景。像导航结果、选项卡片、酒店卡片、工具执行反馈这类结构化输出，往往以新条目插入或尾部内容形态变化的方式出现；如果自动跟随只对文本增长足够敏感，用户就会看到内容已经生成在底部之外，却没有被自然带入视野。另外，当前跟随动作如果依赖瞬时 `scrollTo...` 式跳转，会在连续输出时产生明显的“猛地一拽”感，与聊天流式体验不匹配。

## Goals / Non-Goals

**Goals:**
- 让贴底状态下的自动跟随覆盖所有最新时间线内容类型，而不只限于纯文本增长。
- 让自动跟随默认呈现为平滑、连续的位移动画，降低突兀感。
- 保持用户一旦主动离开底部，就不会被新内容强制打断。
- 为后续实现提供一个单独、可验证的规格边界，避免和当前卡片/思考轨迹改动混在同一上下文里。

**Non-Goals:**
- 不重新设计整个时间线布局或卡片视觉样式。
- 不改变 agent loop、卡片 schema 或工具协议本身。
- 不要求在用户明显离开底部后仍进行“智能追踪”或半自动回拉。

## Decisions

### 1. 自动跟随触发源按“最新可见内容变化”定义，而不是只按文本流式定义

- 贴底状态下，新增 timeline item、最新 item 的卡片 payload 变化、tool feedback 插入，以及导致尾部内容高度继续扩张的更新，都视为 auto-follow 候选事件。
- 这样规格关注的是“用户看到的最新内容是否继续向后长”，而不是底层到底是文本 chunk 还是卡片插入。
- 备选方案是继续只监听文本流式事件，再给个别卡片手工补丁；该方案会让行为分散且容易漏掉新类型，因此不采用。

### 2. 贴底跟随默认使用平滑动画，并对高频更新做节奏收敛

- 当用户仍处于 pinned-to-bottom 范围内时，时间线应通过平滑动画移动到最新内容，而不是瞬时跳底。
- 对连续、高频的更新源（例如流式文本和紧接着的工具阶段输出），实现层可以做轻量合并、节流或取消重入，以避免一边动画一边被下一次跳转打断造成抖动。
- 备选方案是保留文本阶段瞬时跳转、仅对卡片插入做动画；该方案会让一轮回复内部的运动语言不一致，因此不采用。

### 3. pinned-to-bottom 仍然是自动跟随的唯一授权条件

- 自动跟随只在用户仍贴近底部时生效；一旦用户主动上滑离开阈值范围，新的文本、卡片或工具输出都不能强制抢回滚动焦点。
- 当用户重新回到底部后，后续更新再恢复自动跟随。
- 备选方案是根据内容重要性决定是否强制滚动，例如对结果卡片总是抢焦点；这会打断用户复查历史内容，因此不采用。

## Risks / Trade-offs

- [风险] 高频流式更新全部走动画可能出现动画重入、卡顿或“追不上底部” → [缓解] 允许实现层对连续更新做轻量合并，并以“稳定平滑”优先于逐 chunk 精确对齐。
- [风险] 把卡片插入、工具反馈和文本增长统一纳入跟随后，触发面变大，可能暴露更多边界抖动 → [缓解] 统一以尾部内容变化建模，并补充 pinned / unpinned 两类验证用例。
- [风险] 底部阈值过宽或过窄，会导致自动跟随误判 → [缓解] 沿用现有 near-bottom 判定思路，只调整触发源与滚动方式，不在本变更里重做判定策略。

## Migration Plan

- 无数据迁移需求。
- 实现完成后通过 UI 测试与真机手测验证行为即可；若效果不理想，可回退到旧滚动触发逻辑而不影响会话数据兼容性。

## Open Questions

- 当前无阻塞性开放问题；具体动画时长、节流窗口等数值留给实现阶段按体验调优。
